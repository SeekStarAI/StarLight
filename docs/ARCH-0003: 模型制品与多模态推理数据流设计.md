# StarLight 模型制品与多模态推理数据流设计

**文档编号：** ARCH-0003
**状态：** 设计提案，待首条端到端管线验证
**范围：** 模型容器、权重表示、模型家族 lowering、图 IR、设备布局、请求输入与流式输出

本文承接 [ARCH-0002](<ARCH-0002: 模块边界与发行版业务管线契约.md>)，进一步定义模型数据和推理请求如何跨模块流动。本文提出的是设计边界和演进顺序，不代表相关 API 或多模态能力已经实现。

## 1. 设计结论

StarLight 不应把所有格式、模型架构、图执行和设备打包强行压成一个“通用模型文件”。应区分并版本化以下表示：

1. **源制品表示：** 保留 Safetensors、GGUF、ONNX 等外部格式的语义和必要元数据。
2. **逻辑模型包：** 使用格式无关的 manifest、张量目录和编码描述表达模型结构所需的配置及权重视图；这是 loader 与后续模块之间的通用交接面。
3. **模型家族语义表示：** 由 `sl-model-adapters` 把逻辑张量和架构配置映射为模型结构、输入/状态约束、图描述和权重绑定。
4. **图执行表示：** `sl-graph` 将通用计算拓扑编译为可调度、可优化的执行计划；此表示描述计算，不负责重写源制品。
5. **设备物理表示：** backend 根据设备能力选择 kernel、精度和内存布局。硬件专属 packing 是可重建的编译/缓存产物，不是唯一的模型真相。

因此，近期目标应是稳定上述**交接契约**，而不是先设计一种新的磁盘格式。等格式 reader、模型 Adapter 和至少一个 backend 的端到端用例验证了缺口后，再决定是否定义版本化 StarLight on-disk package。

模型文件中的配置和数据均视为不可信输入。模型架构的执行逻辑来自受审查的 StarLight Adapter 和 backend；推理进程不得执行 pickle、任意脚本或模型文件附带的可执行代码。

## 2. 两条数据生命周期

模型加载/编译发生在模型或配置变更时；请求预处理和推理则按每个请求执行。常驻模型应复用已经校验的权重、编译图和设备资源，不应为每个请求重新解析和编译整个模型。

### 2.1 模型制品到可执行模型

```text
Safetensors / GGUF / ONNX / 隔离转换产物
        │
        ▼
sl-model: 容器解析、校验、保留 tensor 与编码语义
        │
        ▼
ModelBundle: 逻辑模型配置 + 张量目录 + 权重数据视图
        │
        ├── sl-precision: 可选的显式量化、反量化或数据布局转换
        │
        ▼
sl-model-adapters: 按架构校验张量并生成通用模型/图描述和权重绑定
        │
        ▼
sl-graph: 图校验、优化、生命周期/内存规划、形成可执行图计划
        │
        ▼
sl-core + sl-device + backend: 绑定设备资源并准备运行
```

`sl-model` 不推断 Transformer 架构、不生成执行命令；Adapter 不重新解析文件容器、不实现设备 kernel；`sl-graph` 不处理源文件名称或请求队列；backend 不修改逻辑模型定义。

### 2.2 请求到流式结果

```text
CLI / SDK 请求
        │
        ▼
Typed Content: 文本、图像、音频、视频帧或结构化内容
        │
        ▼
Tokenizer / modality processor: 产生 token、侧路张量和对齐信息
        │
        ▼
PreparedInput + request options
        │
        ▼
Generation/session controller -> sl-core 单步执行 -> GraphPlan -> backend
        │
        ▼
token IDs / logits / auxiliary outputs
        │
        ▼
解码与 StreamEvent -> SDK 消费者或 daemon 传输层
```

`sl-core` 的单步计算结果与用户看到的文本流不是同一接口。token 解码、内容片段拼装和传输协议应在执行引擎之外完成。

## 3. 格式与职责矩阵

模型家族和模型容器是两个正交维度：一个架构可能以多种容器发布，一个容器也可能承载不同架构。因此不能把“支持 Safetensors”误认为“支持所有 Safetensors 模型”。支持矩阵至少应记录容器、架构/变体、tensor 编码、tokenizer/processor 资产和测试覆盖。

| 输入来源 | 典型内容 | StarLight 接入责任 | 处理原则 |
| --- | --- | --- | --- |
| Hugging Face 风格 checkpoint | `config`、tokenizer/processor 配置、单文件或分片 Safetensors | `sl-model` 读取容器和索引；`sl-model-adapters` 识别明确声明的架构并映射张量 | Safetensors 不包含完整模型定义；架构与配置必须显式提供，分片和 tokenizer 资产需要单独纳入支持矩阵 |
| GGUF | 模型 metadata、词表、张量以及 block/group quantized payload | `sl-model` reader 保留 GGUF tensor encoding；Adapter 负责架构映射 | 不得为了进入统一表示而先将所有权重反量化到 F32；未知量化编码应 opaque 保留或明确拒绝 |
| ONNX | 计算图、initializer/权重及 operator metadata | 作为图导入路径单独评估，由 ONNX importer 将图映射到 `sl-graph` | 它不是普通的“权重容器”；无法映射的 operator 必须报告，不应伪装成家族 Adapter 已支持 |
| PyTorch `.pt` / `.pth` pickle | 权重或可包含 pickle 执行载荷的对象 | 仅考虑隔离的离线转换工具 | 不在在线推理进程中反序列化不可信 pickle |
| 后续设备/框架专用制品 | 设备编译缓存或外部推理引擎格式 | 独立 importer/exporter 或 backend cache | 说明设备和版本兼容条件；不替代通用逻辑模型包 |

第一阶段建议：Safetensors + 一个明确版本的文本模型家族 + CPU backend。GGUF 的首要要求是保真读取和编码描述；ONNX 则以独立图导入能力评估。优先级应由目标用户、可用 fixture 和 backend 能力决定，不按格式数量作为完成度指标。

## 4. 逻辑模型与权重表示

### 4.1 `ModelBundle` 的责任

`ModelBundle` 是 loader 的通用交付物，不是设备可执行文件。当前 `sl-model` 已有 schema 版本、architecture/config、tensor dtype/encoding、共享 payload 视图等基础；后续契约应继续回答以下问题：

- 模型家族标识、架构版本、配置来源和必需 feature 是否显式且可校验；不得仅靠 tensor 名称猜测架构。
- 张量是否有逻辑 shape、逻辑 dtype、物理 storage encoding、分片位置及可选 stride/layout 描述。
- 量化描述是否能区分逻辑精度与存储精度，并携带 group/block size、scale/zero point、packing scheme 和版本。
- tokenizer、词表、媒体 processor 等附属资产如何命名、校验并按需读取。
- 多文件 checkpoint 的 shard index、数据范围、完整性校验和 lazy/mmap 读取如何表达。
- 源格式和源 tensor metadata 如何保留，转换是否发生过、转换参数是什么。

这些字段应按确切需求逐项加入 schema，避免一次性定义尚无生产用例的“万能 manifest”。所有已接受 payload 都必须校验 shape、编码和 byte length；未知编码不得被静默解释为 dense tensor。

### 4.2 逻辑布局与设备布局分离

张量至少区分三层语义：

- **逻辑语义：** 名称/绑定 ID、逻辑维度、元素类型及算子看到的数值含义。
- **存储编码：** F16/BF16、INT4 分组、GGUF block quantization、稀疏编码等 payload 解释方式。
- **设备物理布局：** 针对 SIMD 宽度、tensor core、tile、对齐和内存层级做的 interleave/packing。

`sl-precision` 负责明确声明的数值转换和可复用 packing 算法；设备专属布局由 backend 或其准备工具选择。任何有损转换必须显式配置、记录误差语义并可测试。加载器不得无提示地把全部权重转成 F32，也不得把某个 GPU 的物理 layout 当作跨设备 canonical format。

如需缓存设备预处理结果，cache key 至少应绑定源权重内容哈希、编码/布局版本、精度参数和目标 backend/device capability。缓存失效时应能从逻辑权重或原始制品安全重建。

### 4.3 不同 IR 的边界

`ModelBundle`、模型家族语义描述和 `sl-graph` 的执行 IR 不应合并为一个类型：

- 模型 Adapter 输入架构配置和 `ModelBundle`，输出模型语义、通用图节点及参数绑定；它负责把架构差异解释清楚。
- 图 IR 使用稳定的 operator/type/shape/state 描述，不依赖 `q_proj` 等源 tensor 名称，也不依赖某个家族的 config JSON。
- Graph compiler 可产生多个阶段的计划，例如 prefill 与 decode；计划描述依赖、shape specialization、临时内存和可并发节点。
- backend 再将计划降低为设备 kernel、内存资源和队列提交；设备不可用的 operator 应有显式 fallback 或可诊断错误。

图 IR 应能表达符号维度、运行期 binding、KV cache 等跨 step 状态资源，以及必要的读写副作用。图优化不得把可观察的状态更新重排成错误语义。对生成式模型，应优先编译可复用的 prefill/decode 子图，而不是将未知长度的整个自回归生成循环静态展开。

## 5. 模型家族 Adapter 的契约

`sl-model-adapters` 应以家族/架构变体为单位提供明确的支持矩阵。每个 Adapter 至少负责：

- 声明支持的 architecture ID、config/schema 版本和必要 feature；验证缺失或冲突字段。
- 把源 tensor 名称、shape、dtype/encoding 映射到稳定参数角色；错误中指出缺失、重复或 shape 不匹配的权重。
- 描述模型层结构、embedding/norm/attention/MLP/MoE 等已支持组件，以及其所需的通用 operator 能力。
- 明确 prefill、decode、KV cache/state、位置编码和输入输出 binding 的语义。
- 对未支持的变体或 operator 返回可诊断错误，不以“同属某个家族”为由猜测兼容。
- 提供最小模型配置与 tensor fixture，验证 lowering 输出的结构和绑定。

Adapter 是编译期 Rust 代码，不是模型文件中的动态脚本。Tokenizer 和图像/音频预处理不应自动归入架构 Adapter；Adapter 可声明输入要求和 processor 元数据，但实际预处理应走独立的输入处理接口。

## 6. 请求输入与多模态预处理

面向用户的 API 不应只有 `&str`，也不应把任意媒体塞进不透明的 token 数组。建议将一个请求表达为有序的消息和内容片段，概念上包含：

- `Text`：UTF-8 文本及其所在消息角色/边界。
- `Image`：受限字节、文件/对象引用或解码后的图像资源；附媒体类型和安全限制。
- `Audio`：输入或输出音频资源、编码/采样率信息及任务语义，例如识别、感知或语音生成。
- `VideoFrame`：带时间戳的图像帧序列；避免把完整视频无边界地复制进单一请求缓冲区。
- `Sequence`：多肽/蛋白质或核酸等生物序列，显式携带 alphabet、链/片段边界及必要的修饰信息；不能假设通用文本 tokenizer 能正确处理它。
- `Structured`：有明确 schema 的空间、动作或其他结构化数据；未知 schema 应拒绝或作为 opaque 数据保留。

媒体字节应通过受限 buffer 或资源句柄传递，不应默认在 JSON 文本中 base64 展开。每种输入需校验尺寸、时长、帧数、编码和访问权限，并设置资源上限。

Tokenizer/processor 将用户内容转换为 `PreparedInput`。它除了 token IDs，还可能包含图像 patch/embedding 输入、音频特征、生物序列编码、时间戳、segment 边界、模态标记、mask 和原内容到 token/tensor 的对齐信息。生物序列必须按模型声明的 alphabet、修饰和 tokenizer 规则校验，保留 residue/位置到 token/tensor 的映射。`sl-core` 只消费已校验的模型输入 binding，不解析 URL、JSON、图片文件或音频容器。

Tokenizer、image/audio/video processor 可来自适配库或未来的独立输入处理组件；当前不应为未支持的 modality 预先固定过多 crate/API。首个文本闭环可先以 token IDs 输入验证执行链，再加 tokenizer；视觉、音频、视频各自需要真实 processor、fixture 和 golden tests 后才计入支持。

## 7. 推理循环与流式输出

需要区分三个层级：

1. **执行 step：** `sl-core` 接收已绑定的输入/state，执行图并返回 logits、token IDs 或模型定义的 auxiliary outputs；它不写 socket、不格式化文本。
2. **生成控制：** 在多个 step 之间维护采样参数、停止条件、tokenizer 状态和 KV cache 生命周期。建议作为共享的 generation/session API，而不是放进 `sl-graph`、backend 或 daemon；首个实现需明确它由哪个 crate 承载，再让 Nano 与 Cluster 复用同一实现。
3. **事件呈现与传输：** SDK 把生成结果转换成有序事件；daemon 选择 SSE/gRPC/其他服务协议并做请求复用。网络协议不进入 `sl-core`。

概念性的 `StreamEvent` 应支持：开始、增量文本/token、结构化序列或多模态输出片段、用量统计、完成原因和错误。具体 v1 可以只实现文本/token delta，但协议要保留 request ID、序号、finish reason 和错误分类的扩展位置。不要把“每个 token 一条文本字符串”作为唯一表示，因为 UTF-8 解码边界、工具调用、生物序列标注和非文本输出都可能跨 chunk。

流式 API 还必须定义：

- 事件顺序及完成/错误事件是否恰好一次；
- 消费者变慢时的有界缓冲和 backpressure，不允许无界积压；
- 客户端取消如何停止后续 decode 并释放 session/KV cache；
- 断开连接、deadline、模型错误和设备错误的区分；
- token IDs、解码文本、logits 是否可选暴露及其安全/兼容语义。

Rust SDK 可以提供拉取式 iterator/stream 或 channel，但底层推理 step 不应强行绑定某个 async runtime。daemon 负责把取消、deadline 和网络背压传递到 generation/session 控制面。

## 8. 调度与图执行的交界

prefill 与 decode 的工作形态不同：prefill 通常一次消费较长上下文，decode 每个活跃序列逐步追加 token。图编译应允许运行期输入 binding、受控的动态维度或 shape buckets；请求 scheduler 决定哪些序列组成 batch，图引擎执行该 batch 对应的图计划。

职责划分如下：

- `sl-graph`：节点依赖、图内并发、图优化、执行计划和 scratch/memory lifetime。
- backend/`sl-device`：设备队列、命令提交、设备同步及 kernel 资源。
- generation/session 层：单个请求的 token loop、停止条件和会话状态。
- `sl-daemon` 或外部 scheduler：跨请求准入、排队、batch 组成、优先级和服务级取消。

Continuous batching 等策略不得硬编码为模型格式或图 IR。图计划需要公开 scheduler 所需的 shape/state/capability 约束，但不接管请求优先级。

## 9. 验收与演进顺序

建议以真实纵向切片逐层确认数据契约：

1. **文本、单格式、单家族、CPU：** Safetensors checkpoint -> `ModelBundle` -> `sl-model-adapters` lowering -> prefill/decode graph plan -> CPU execution -> token IDs/logits；带模型 fixture 和数值基线。
2. **格式保真：** 增加分片 checkpoint 或 GGUF reader，验证未知/分组量化编码不会被静默破坏；记录各 family-format 组合的支持状态。
3. **文本 SDK/CLI：** 加 tokenizer、generation session 和有界流式文本事件；CLI 与 SDK 共用同一 pipeline。
4. **硬件布局：** 为第二种 backend 加设备能力协商和可重建的目标布局缓存；验证通用图与逻辑权重不依赖首个 backend。
5. **多模态：** 逐种加入图像、音频或视频 processor，定义 `PreparedInput` 的侧路 tensor/alignment，并为每种 modality 提供资源限制、fixture 和跨模块 golden tests。
6. **服务与分布式：** 定义 request scheduler 如何承载有状态 session、取消/backpressure，以及必要时如何接入可选通信组件。

每个支持项都应以组合状态记录，例如 `Safetensors + family-X + CPU + text`，而不是只标记“支持某格式”或“支持某家族”。架构、格式、量化编码、tokenizer/processor、backend 和 streaming feature 应分别版本化和测试。

## 10. 当前明确不承诺的事项

- 当前 `sl-model` 主要提供 `ModelBundle` 与 Safetensors reader；它不是完整的 Hugging Face checkpoint loader，也不是代码执行环境。
- 当前 `sl-model-adapters` 已创建独立仓库，但尚无 Cargo package 或 Adapter 实现。
- 当前 `sl-graph`、`sl-core`、设备后端还没有完整执行 API；本文的 IR/plan 名称是设计概念，不是现存 Rust 类型。
- 当前没有通用多模态 processor、tokenizer、generation stream 或网络流式协议。
- 当前不定义 StarLight 专有的通用模型磁盘格式，也不承诺 GGUF、ONNX、PyTorch pickle 或任何具体模型家族已可推理。

第一条实现链应先解决文本小模型的格式读取、家族映射、图构建和 CPU 单步正确性，再用真实需求推动量化保真、动态 batch、流式事件和多模态接口；不要让未实现的远期需求阻塞最小可验证管线。
