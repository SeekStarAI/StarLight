# ARCH-0008：推理基础设施能力矩阵与缺口清单

**状态：** Living document（随实现与模型目录同步更新）
**最后更新：** 2026-10-18
**适用范围：** `sl-model` → `sl-ir` → `sl-graph` → `sl-core` → `sl-device` → `backend-*` → `starlight-runtime` 的推理主链路。
**不包含：** 训练、微调、InfrArray 控制面与产品排期。

本文回答两个问题：

1. 当前引擎**已经具备**哪些推理基础设施；
2. 面对主流开源模型家族，**还缺**哪些基础设施，按什么顺序补。

状态定义：

| 状态 | 含义 |
| --- | --- |
| **Done** | 代码已落地，且 workspace 内有测试覆盖 |
| **Partial** | 契约或单条路径已存在，但不足以支撑生产使用；边界必须写明 |
| **Missing** | 没有实现；不能靠现有算子/配置绕过 |

“模型目录存在”不等于“引擎支持”。家族目录里的 `structural / planned / blocked` 是适配状态，不是引擎能力承诺。

---

## 0. 结论摘要

当前 StarLight 是一个 **dense、F32、decoder-only、连续 KV cache、单进程** 的参考推理引擎：

- 已支持 MHA / GQA / MQA（通过 `CausalAttention.kv_heads`）、NeoX/GPT-J RoPE、RMSNorm、SwiGLU、causal attention、KV append、uniform batch 的 prefill/decode；
- 已支持 `Program → CommandBuffer` 编译、能力协商、`SwiGlu` / `RmsNormMatMul` 分解、静态 scratchpad 内存计划；
- 已支持 CPU 参考后端全部 18 个 `OpCode`，以及 token-ID 端到端 fixture；
- 已支持 `llama` / `dense` 家族的 lowering，并建立 17 个模型家族目录与 65 个常见型号描述。

因此，**结构上最接近可跑的是 Llama 2/3、Yi、R1-Distill-Llama 这类无 bias、RMSNorm + SwiGLU + RoPE + GQA 的 dense 模型**。但即使这些模型，也还缺 tokenizer、采样器、真实 checkpoint fixture 与文本 CLI，不能算“端到端可服务”。

当前**不能**支持的主流结构包括：

- linear bias（Qwen2.5）；
- RoPE scaling / partial RoPE / ALiBi（Llama 3.1+、GLM、Falcon）；
- sliding-window attention（Mistral 7B、Mixtral、Gemma 2/3）；
- GeGLU、LayerNorm、Gemma 的 `1 + weight` RMSNorm 语义；
- QK-Norm（OLMo 2；Qwen3 待核实）；
- MoE 路由与专家执行（Mixtral、DeepSeek V2+、Qwen3 MoE、GLM-4.5、Hunyuan-Large、ERNIE 4.5）；
- MLA（DeepSeek V2/V3/R1）；
- 多模态编码器与投影（Gemma 3、Qwen2.5-VL、Pixtral、Yi-VL、MiniCPM-V）；
- 分页 KV、连续批处理、采样、tokenizer、daemon/OpenAI 协议；
- 量化权重的可执行路径（IR 有 encoding，backend 没有量化内核）；
- F16/BF16 权重直接执行（算子端口与 device 目前都是 F32）。

| L5 验证 / 工具 | 真实 checkpoint、golden、CI、性能基准 | workspace、`tests/golden-baselines` |

### 2.1 已具备但只是“参考实现”的部分

- **CPU backend 是参考实现**：正确性优先，无 SIMD、无多线程、无量化内核；
- **uniform batch**：同一 step 内所有序列共享 `seq_len`，没有 per-sequence 长度、padding mask 或连续批处理；
- **静态内存计划**：只规划 `Temp`，KV 固定预分配，没有分页/回收；
- **runtime 只到 token-ID**：没有 tokenizer，所以 `run --input-ids` 不是文本推理。

## 3. 缺口登记

优先级：

- **P0**：不补就无法支持主流 dense 模型或无法形成文本端到端；
- **P1**：能跑之后决定服务能力与效率；
- **P2**：大模型/多模态/多设备能力。

| ID | 缺口 | 优先级 | 影响 | 验收标准 |
| --- | --- | --- | --- | --- |
| G-01 | Linear bias（`MatMulNT` 后的 `[out]` bias 广播加） | P0 | Qwen2.5、部分 Phi | bias 可作为独立算子或 fused 参数；Qwen2.5-7B 能 lower + compile + 数值对齐 |
| G-02 | RoPE scaling（linear / dynamic / YaRN / Llama 3 分段缩放） | P0 | Llama 3.1/3.2/3.3、Phi-4、部分 InternLM | `Rope` 增加 scaling 描述；长上下文位置数值测试通过 |
| G-03 | Partial RoPE 与 ALiBi | P0 | GLM、Falcon 1/2、Baichuan（按版本） | `Rope` 支持 `rotate_dim`；ALiBi 作为 attention bias 路径；对应模型 lower + compile |
| G-04 | Sliding-window attention | P0 | Mistral 7B、Mixtral、Gemma 2/3 | `CausalAttention` 增加 window 参数；window mask 单测与模型编译通过 |
| G-05 | GeGLU | P0 | Gemma 全系 | `GeGlu` 算子或可分解实现；Gemma dense lower + compile |
| G-06 | LayerNorm 与 Gemma RMSNorm offset | P0 | Phi-2、Gemma | 支持 LayerNorm；RmsNorm 支持 `1 + weight` 语义；数值测试 |
| G-07 | QK-Norm（q/k 的 per-head RMSNorm） | P0 | OLMo 2、Qwen3（待核实） | adapter 在图里插入 q/k norm；OLMo 2 / Qwen3 dense 编译通过 |
| G-08 | MoE router / top-k / expert dispatch | P2 | Mixtral、DeepSeek V2+、Qwen3 MoE、GLM-4.5、Hunyuan-Large、ERNIE 4.5 | 路由、专家权重布局、capacity/overflow 策略确定；至少一个 MoE 模型数值对齐 |
| G-09 | MLA（Multi-head Latent Attention） | P2 | DeepSeek V2/V3/R1 | 新 state 布局与 attention 算子；DeepSeek-V2 小切片数值对齐 |
| G-10 | 多模态编码器 / projector / image token | P2 | Gemma 3、Qwen2.5-VL、Pixtral、Yi-VL、MiniCPM-V | 视觉塔接入协议、image token 展开、预处理边界确定 |
| G-11 | Embedding scaling / 家族特有归一化 | P1 | Gemma、MiniCPM | 由 adapter 显式插入 `Scale` 或新算子；数值测试 |
| G-12 | Tokenizer | P0 | 所有文本模型 | 独立 `sl-tokenizer` 或 adapter 依赖；encode/decode 与官方 tokenizer 对齐 |
| G-13 | 采样器（greedy / top-k / top-p / temperature） | P0 | 所有生成模型 | `Engine` 或 runtime 提供采样；固定 seed 可复现 |
| G-14 | 真实 checkpoint fixture 与文本 CLI | P0 | 所有模型 | 一个 F32 Llama 3 8B（或 tiny 真权重）从文件到文本输出，golden logits 对齐 |
| G-15 | F16/BF16 权重执行 | P0 | 主流 checkpoint（多为 BF16） | device 支持 f16/bf16 或 adapter 做受控 upcast；数值/内存边界写明 |
| G-16 | 量化权重绑定与量化内核 | P1 | INT4/INT8 部署 | `PackedLayout` + scale 绑定 + quantized matmul；`sl-core` 放开非稠密 Param |
| G-17 | 分页 KV cache | P1 | 高并发服务 | block table、按页分配/回收、attention 读页；与连续批处理联调 |
| G-18 | 连续批处理 / 变长序列 | P1 | 服务吞吐 | per-request seq_len、slot 管理、调度器；与 Engine 解耦 |
| G-19 | CUDA / Vulkan 内核与 SIMD | P1 | 实际性能 | 至少一个 GPU 后端通过 18 算子一致性测试；CPU SIMD 可选 |
| G-20 | `sl-daemon` HTTP / OpenAI / 流式 | P1 | 服务化 | `/v1/completions`、`/v1/chat/completions`、SSE 流式、取消 |
| G-21 | Sharded Safetensors / GGUF | P1 | 大模型加载 | index 加载、多文件权重、GGUF block quantization（后续） |
| G-22 | 投机解码 | P2 | 延迟优化 | draft/target 协议、接受率统计；不影响主路径正确性 |
| G-23 | 多设备 / 专家并行 | P2 | 超大模型 | 设备拓扑、权重分片、通信原语；v1 不做 |
| G-24 | CI、golden baseline、性能基准 | P1 | 回归与发布 | CI 跑 workspace 测试；golden logits；每后端最小 benchmark |

### 3.1 P0 缺口的设计注意

**G-01 bias**：不要在每个家族里手写 `Add`。`Add` 要求同 shape，`[out]` 对 `[1, seq, out]` 需要广播。优先定义 `Bias`（或 `MatMul` 的 bias 输入），再让 adapter 决定是否融合。

**G-02 RoPE scaling**：`Rope` 目前只有 `variant` 与 `theta`。scaling 是**位置映射**，不是简单改 theta；Llama 3 的分段缩放与 YaRN 需要显式描述，否则长上下文会静默错误。

**G-03 partial RoPE / ALiBi**：partial RoPE 需要 `rotate_dim`；ALiBi 是 attention score 的加性 bias，不能复用普通 `Add`。两者都要进 `Signature` 或 attention 参数。

**G-04 sliding window**：`CausalAttention` 目前只有 causal mask。window 是 mask 语义的一部分，必须在 IR/算子层表达，不能靠截断 KV 模拟（会改变 state 语义）。

**G-05 GeGLU**：`SwiGlu` 的计算是 `down(silu(gate) * up)`；GeGLU 把 `silu` 换成 `gelu`。可以新增 `GeGlu` composite，或让 `SwiGlu` 参数化激活函数；不要复制整张图。

**G-06 norm 变体**：LayerNorm 与 RMSNorm 的均值/偏置语义不同；Gemma 的 RMSNorm 使用 `1 + weight`。这些是数值契约，必须显式建模，不能由 adapter 私自改权重。

**G-07 QK-Norm**：per-head RMSNorm 理论上可用现有 `RmsNorm` 表达（对 `[B, H, S, D]` 的最后一维归一化），但要确认权重形状、是否在 RoPE 前、是否有 offset。先补 adapter 与测试，不一定要新算子。

**G-12 / G-13 / G-14 / G-15**：这四项决定“能不能文本推理”，不是模型结构问题。建议作为独立里程碑，与算子补充分开推进。

## 5. 推荐顺序

### Stage A：Dense 结构补齐（P0）

目标：让主流 dense 家族能 lower + compile，不要求服务化。

1. G-01 bias；
2. G-02 RoPE scaling；
3. G-03 partial RoPE / ALiBi；
4. G-04 sliding window；
5. G-05 GeGLU；
6. G-06 LayerNorm / Gemma norm offset；
7. G-07 QK-Norm（优先 adapter，确认是否需要新算子）。

完成标准：每个缺口至少有一个家族 fixture 通过 `Program::validate` + `sl-graph::compile`，并有数值测试。

### Stage B：文本端到端（P0）

目标：一个真实 checkpoint 从文件到 token。

1. G-12 tokenizer；
2. G-13 sampler；
3. G-14 真实 checkpoint fixture + 文本 CLI；
4. G-15 F16/BF16 策略（upcast 或混合精度）。

完成标准：Llama 3 8B（或等价 tiny 真权重）`run --prompt` 输出可复现 token，logits 与参考实现对齐。

### Stage C：服务与效率（P1）

1. G-16 量化绑定 + 量化内核；
2. G-17 paged KV；
3. G-18 连续批处理；
4. G-19 CUDA/Vulkan（或先 CPU SIMD）；
5. G-20 daemon/OpenAI/流式；
6. G-21 sharded Safetensors / GGUF；
7. G-24 CI/golden/benchmark。

### Stage D：大模型与多模态（P2）

1. G-08 MoE；
2. G-09 MLA；
3. G-10 多模态；
4. G-22 投机解码；
5. G-23 多设备/专家并行。

依赖关系：

- Gemma 需要 G-04 + G-05 + G-06；
- DeepSeek 需要 G-08 + G-09；
- 量化服务需要 G-16，且依赖 G-15 的 dtype 策略；
- 连续批处理依赖 G-17 才能发挥价值；
- 多模态依赖 G-10 与 tokenizer/预处理边界。

## 6. 暂不做 / 明确不承诺

- 训练、微调、对齐；
- PTH/PyTorch pickle 在推理进程内反序列化；
- 一次支持全部 17 个家族；
- 与 vLLM/TensorRT-LLM 的逐 benchmark 对齐（属于 InfrArray 认证矩阵）；
- v1 的跨节点张量并行；
- 非 NVIDIA/非 Linux 的正式支持。

## 7. 维护规则

1. **新增家族**：先在 `sl-model-adapters/src/families/<family>/` 建 `README.md` + `models.toml`，并在本文第 4 节加一行；
2. **新增型号**：更新对应 `models.toml`，标注 `structural / planned / blocked` 与 blocker；
3. **新增算子**：同时更新 `docs/ARCH-0004`、`sl-ir::Signature`、backend capabilities 与本文第 2/3 节；
4. **标记 Done**：必须有 workspace 测试证据；只有设计或目录不算 Done；
5. **标记 Partial**：必须写清边界（“只支持什么、不支持什么”）；
6. **每个里程碑结束**：复核第 3 节缺口表，删除已关闭项，新增新发现的缺口。

本文与 `docs/ARCH-0004`、`docs/ARCH-0006` 冲突时：

- 算子/ABI 语义以 ARCH-0004 为准；
- 模型 lowering 与家族目录以 ARCH-0006 为准；
- 本文只负责“能力现状 + 缺口 + 顺序”，不重复定义 ABI。
