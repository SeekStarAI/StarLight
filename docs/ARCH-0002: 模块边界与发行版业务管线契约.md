# StarLight 模块边界与发行版业务管线契约

**文档编号：** ARCH-0002
**状态：** 第一阶段工程基线
**范围：** 模块职责、依赖方向、调度层次、发行版入口与端到端验收

本文将 StarLight 的架构目标约束为可实现、可测试的模块契约。本文中的“必须”“不得”表示后续实现和接口评审要求；标注为“目标”或“尚未实现”的能力不代表当前代码已提供。

当本文与 RFC-0001 中的模块边界或仓库描述不一致时，以本文作为当前模块协作与发行版装配的基线。RFC-0001 保留为早期架构规划和任务拆分记录，不能单独作为功能已交付的证据。

## 1. 系统分层

StarLight 至少区分以下四类职责，不能把它们统称为一个“调度器”：

1. **图内并发组织：** `sl-graph` 根据节点依赖形成可执行计划，并表达可并发的计算。它不管理用户请求队列，也不直接管理进程生命周期。
2. **设备执行提交：** `sl-device` 定义设备、资源和提交接口；具体 backend 将计算映射为设备内核并提交到设备队列。它不决定用户请求优先级。
3. **单模型运行时：** `sl-core` 装配图、权重和设备，维护推理执行所需状态，并驱动一次或多次模型执行。它不负责网络服务、跨请求排队或批处理策略。
4. **请求与服务编排：** `sl-daemon` 或外部调度系统负责会话、队列、准入、批处理和服务生命周期。端侧发行版可不包含 daemon，由 SDK 调用方直接驱动运行时。

分布式通信是可选能力。通信组件负责设备或节点之间的数据交换与集合通信，不替代图内依赖管理、请求调度或设备内核。

### 2.1 `sl-model-adapters` 的归属

模型文件格式与模型网络结构是两个不同问题。`sl-model` 负责把容器解析为通用 `ModelBundle`；例如 Llama 类架构如何把 tensor 名称和配置映射成 Transformer 图，由 `sl-model-adapters` 中的模型家族 Adapter 完成。Adapter 依赖 `sl-model` 与 `sl-graph`，输出图描述及权重绑定，不得让 `sl-model` 反向依赖图引擎，也不得让 `sl-core` 依赖具体模型家族。

StarLight 主仓库已将 `https://github.com/SeekStarAI/sl-model-adapters` 登记为 `crates/sl-model-adapters` submodule。仓库只记录 submodule URL 和固定提交；Adapter 源码在该独立仓库维护。当前远端初始提交仅包含 README 和 LICENSE，尚无 `Cargo.toml`、公开 API 或可调用实现，因此它目前不是 Cargo workspace member。

仓库边界采用“一个 Adapter 仓库承载多个模型家族”的方式，不为每个家族立即拆分 Git 仓库。仓库建立 Rust package、确定公共 crate/API 并实现首个家族后，再将该 package 加入根 Cargo workspace 和发行版依赖；在此之前不得在根 manifest 中引用不存在的 package。家族间若需不同依赖或版本节奏，之后可在 Adapter 仓库内拆成多个 package，但不改变 `sl-model` 与 `sl-graph` 的职责边界。

发行版可以负责选择 Adapter，但模型配置校验、张量映射和图 lowering 不得长期藏在发行版 `main.rs` 中。公共 Adapter API 应先由一个可运行纵向切片验证，再通过第二个模型家族验证抽象是否可复用，避免过早冻结无实现支撑的通用接口。

## 3. 依赖方向与数据契约

目标依赖方向如下。箭头表示“上游可以调用/依赖下游”，反向依赖禁止形成：

```text
CLI / SDK
    │
    ▼
发行版 Pipeline（composition root） ──────> sl-daemon（集群可选）
    │                                            │
    ├──> sl-model ──> ModelBundle                └──> sl-core
    ├──> sl-precision（离线或准备阶段）
    ├──> sl-model-adapters ──> sl-graph
    └──> backend 选择 ──> sl-device <── backend-*
                               ▲           │
                               └── sl-core ┘

可选分布式通信能力由需要它的图执行/backend/发行版通过明确接口接入；
它不能成为端侧单设备 Pipeline 的必需依赖。
```

发行版需要直接调用哪个 crate 的公开 API，就必须在自己的 `Cargo.toml` 中声明该依赖；不得依赖 Cargo 传递依赖碰巧暴露的 crate。模块间只传递版本化、可验证的数据契约，不传递 CLI 参数对象或某个 backend 的私有类型。

关键交接对象的目标语义：

- `ModelBundle`：格式无关的模型 metadata、张量目录、逻辑形状、编码描述及共享 payload 视图。它不是可执行图。
- `LoweredModel`（目标类型）：模型 Adapter 产出的通用图描述与参数绑定。不得携带源文件解析器或网络请求状态。
- `GraphPlan` / `CompiledGraph`（目标类型）：图验证、优化和内存规划后的可执行描述。它不能绑定某个具体服务的请求队列。
- `Device` / `Backend`（目标接口）：设备能力和资源提交入口。buffer、queue、同步及错误含义由 `sl-device` 统一定义。
- `Engine` / `Session`（目标接口）：`sl-core` 对编译图和设备的运行时装配及一次会话的执行状态。具体命名以各 crate API review 为准。

这些名称是契约对象的概念名，不是声称当前代码已公开对应 Rust 类型。正式 API 必须在模块仓库中实现并测试后，才能由发行版调用。

## 4. 发行版业务管线

发行版必须提供一个能把多个模块串起来的可调用业务入口。建议每个发行版采用同一结构：

- `src/lib.rs`：稳定的 SDK/facade，暴露配置、Pipeline/Engine 创建、模型加载和推理调用；
- `src/main.rs`：薄 CLI，将参数解析为配置并调用同一套库 API，不放模型推理逻辑；
- `tests/pipeline.rs`：跨 crate 集成测试，验证公开 API 的真实调用链，而不只测试各 crate 单体。

Nano 的最小推理 Pipeline 顺序：

1. CLI/SDK 校验配置、模型路径、backend 与输入 token IDs。
2. 通过 `sl-model` reader 得到已校验的 `ModelBundle`。模型格式要求的 architecture/config 由调用方配置或显式 metadata 提供。
3. 调用 `sl-model-adapters` 中选定的模型家族 Adapter，将 `ModelBundle` 转为通用图和权重绑定。
4. 选择已编译进发行版的 backend，创建 `sl-device` 设备实例，并读取设备能力。
5. 调用 `sl-graph` 编译/规划图，再由 `sl-core` 组装运行时对象。
6. 对输入 token IDs 创建执行上下文；调用 `sl-core` 的执行 API。`sl-graph` 管理图内依赖与并发，backend 提交设备工作。
7. 将输出 token IDs/logits 和诊断信息返回给 SDK 或 CLI。

第一条闭环可以直接接收 token IDs 并返回 token IDs/logits，避免将 tokenizer 误塞进设备或图模块。面向文本的 tokenizer、采样器和流式输出应作为明确的上层组件/API 后续接入。

Cluster 在上述模型执行链路外增加服务编排：daemon 接收请求、做准入/队列/批处理，再把已准备好的执行任务分派给 `sl-core`；只有图或 backend 需要跨设备执行时，才接入分布式通信设施。请求排队不能转交给 `sl-graph`。

离线模型转换是另一条 Pipeline：模型 reader -> 精度转换 API -> 模型 writer/转换器。`sl-precision` 当前 CLI 是 Safetensors 转换前端；最终面向用户的命令可以由发行版或独立工具 crate 提供，但不得把转换命令嵌入推理热路径。

## 5. CLI/SDK 最低交付标准

发行版首个端到端里程碑必须交付至少一种真实可运行入口，而非只创建空 `main.rs`：

- SDK 至少能从配置构造 Pipeline/Engine、加载受支持模型、执行一个输入 token 序列并取得结果；
- CLI 至少提供等价的 `infer` 子命令，并通过 SDK/facade 调用同一 Pipeline；
- 最小命令可采用 token ID 输入，例如 `starlight-nano infer --model tiny-model.safetensors --backend cpu --input-ids 1,2,3`。命令和参数是建议接口，须在实现时结合实际 tokenizer/模型支持确认；
- 本地 pipeline 集成测试必须在真实公开 API 上依次调用模型 reader、`sl-model-adapters`、图编译、backend 选择、运行时构建和执行。缺失的组件可先用 mock backend/小型 fixture 代替，但测试必须能证明模块边界和调用顺序；
- 至少有一个 CPU 小模型/fixture 的非 mock 测试证明端到端结果可重复，并提供预期输出或数值容差；
- CLI 与 SDK 的结果、错误分类和配置语义一致。CLI 仅负责解析、显示和退出码，不得复制 Pipeline 逻辑。

在上述标准通过前，发行版应标注为 scaffold/实验性，不应宣称已支持完整模型推理。

## 6. 实现与验证顺序

1. **冻结交接契约：** 确认 `ModelBundle -> sl-model-adapters -> GraphPlan -> Device -> Engine` 的公开对象、错误语义、所有权和版本策略；在 Adapter 仓库建立 package 和首个可测 API 后，再将其接入 workspace。
2. **图与设备可测试骨架：** `sl-graph` 有图验证/计划测试，`sl-device` 有 mock 实现约定；不以 crate 能编译代替接口验收。
3. **运行时与后端纵向切片：** `sl-core` 通过 mock backend 构建并执行最小图；CPU backend 再替换 mock，覆盖小型 fixture。
4. **发行版集成：** `starlight-nano` 提供 SDK facade 和薄 CLI；集成测试真实串接上游模块；固定模型格式、backend 与输入输出示例。
5. **服务化扩展：** `sl-daemon` 增加并发请求生命周期和调度测试；单机 Nano 路径不得因此强制依赖 daemon。
6. **分布式扩展：** 在存在真实多设备场景和性能/正确性测试后，定义可选通信 API 与 Cluster 装配，不预先将未实现能力写成硬依赖。

每个阶段都须满足：模块单测覆盖本模块责任；跨模块数据交接有契约测试；接口变更同步更新模块文档、workspace 锁定的 submodule/依赖版本及发行版集成测试。离线解析/转换和构建阶段可以分配内存；运行期是否要求零分配必须按具体 API 路径用 allocator 测试验证，不得仅以文档承诺代替测量。

## 7. 当前缺口

按当前 workspace 状态，以下项目是打通发行版业务 Pipeline 的前置工作，而不是已有功能：

- `sl-graph`、`sl-device`、`sl-core` 与 CPU/Vulkan backend 尚无可调用的完整执行契约；
- `sl-model-adapters` 已接入为 submodule，但还没有 Cargo package、公开 API 或模型家族实现；
- Nano/Cluster 只有空入口，没有共用的 SDK facade、CLI 命令或跨 crate 集成测试；
- `sl-model` 尚无模型文件写入/通用导出 Pipeline，`sl-precision` CLI 仅覆盖当前定义的 Safetensors 量化格式；
- Cluster 请求调度、可选分布式通信、tokenizer/采样等上层能力仍需分别定义边界。

因此第一条可执行纵向切片应优先选择一个小型模型、一种格式和 CPU backend，贯通 Nano 的 SDK/CLI；不要并行扩展格式、硬件与集群能力，直到该调用链可重复构建、测试和运行。
