## 1. 系统工程架构理论与核心准则

StarLight 采用分层微内核架构，将大模型推理过程解耦为**离线确定性规划**与**在线无状态步进**两个严格隔离的阶段。系统设计遵循以下四项工程理论：

  

### 1.1 控制与计算分离（Control-Compute Separation）

系统将“资源调度策略”与“算子指令执行”彻底剥离。核心层不维护请求队列、网络套接字或线程生命周期，仅提供基于状态的单步前向传播函数。计算拓扑在初始化期编译为静态指令序列，运行期仅更新输入描述符（Descriptor）与物理内存页表偏移。

  

### 1.2 静态生命周期内存管理（Static Lifetime Memory Planning）

系统在推理循环中消除一切动态堆内存分配（Zero-Allocation at Runtime）。

  

-   **激活值工作区（Scratchpad Arena）：** 在图编译阶段，根据张量的生命周期区间（Live Range）执行区间图着色算法，计算所有中间张量在单一连续内存块中的静态字节偏移（Offset），实现空间复用。
    
      
    
-   **分页键值缓存（Paged KV-Cache）：** 逻辑连续的序列上下文映射至固定大小的物理内存块（Block/Page）。通过扁平化页表进行基址加偏移寻址，消除动态扩容引发的内存拷贝与碎片。
    
      
    

### 1.3 片上缓存驻留与延迟剔除（Tile Residency & Early Culling）

针对推理访存带宽受限特征，引入分块（Tiling）与两阶段执行机制：

  

-   **临时资源（Transient Buffer）：** 显式声明生命周期不跨越分块边界的中间张量（如局部 Attention Logits），在硬件后端直接绑定至片上高速缓存（SRAM / Shared Memory / L1-L2 Cache），禁止产生主存写回操作。
    
      
    
-   **预剔除机制（Early Culling）：** 在执行主存密集型读取前，通过轻量级元数据评估块激活权重，直接跳过低于阈值的物理页加载。
    
      
    

### 1.4 硬件感知的数据排布（Hardware-Aware Memory Layout）

权重与激活数据在加载或离线预处理期，按照目标硬件向量宽度（如 32/64 字节对齐、矩阵计算单元通道交织格式）完成物理重排（Packing），确保算子执行期可直接发起对齐的向量流式读取指令，消除运行期转置开销。

  

## 2. 核心子系统边界与接口契约

整个系统由五个正交的核心模块组成。各模块通过严格的数据结构与 Rust `Trait` 交互，无双向依赖。

  

Plaintext

```
[发行版装配层: Distro Entrypoint]
       │
       ├──> [sl-daemon] (进程监管 / IPC / 会话请求排队 / 全局页池分配策略)
       │         │
       └──> [sl-core]   (无状态单步执行器 / 模型拓扑组装 / 页表地址解析)
                 │
                 ├──> [sl-graph]     (DAG 优化 / Pass 融合 / 静态内存偏移计算 / 指令录制)
                 ├──> [sl-precision] (多比特量化编码 / 硬件对齐重排 / 精度校准)
                 └──> [sl-device]    (VDI 硬件抽象层接口)
                           │
                           ├──> [backend-cpu]
                           ├──> [backend-vulkan]
                           ├──> [backend-cuda]
                           └──> [3rd-party-backend]

```

### 2.1 `sl-precision`（精度与数据排布模块）

-   **输入：** 原始浮点权重字节流、目标精度配置（FP8/INT4/INT2、Group Size）、目标硬件对齐参数。
    
      
    
-   **输出：** 交织重排后的连续字节缓冲区（`PackedBuffer`）、缩放因子与零点元数据表。
    
      
    
-   **独立性：** 零硬件上下文依赖，可独立编译为离线模型转换 CLI 工具或被第三方框架直接引用。
    
      
    

### 2.2 `sl-graph`（静态图优化与规划模块）

-   **输入：** 算子节点拓扑定义、输入输出张量形状与数据类型。
    
      
    
-   **输出：** 融合后的线性指令队列（`CommandBuffer`）、全局 `Scratchpad` 所需总字节数及每个张量的静态偏移表（`MemoryPlan`）。
    
      
    
-   **核心功能：** 算子融合 Pass（如 `RMSNorm + Linear`）、局部暂存资源标记、区间着色内存规划。
    
      
    

### 2.3 `sl-device`（虚拟设备抽象接口 VDI）

-   **职责：** 定义底层硬件驱动必须实现的标准契约，不包含任何具体实现代码。
    
      
    
-   **核心接口定义：**
    
      
    

Rust

```
pub trait BackendDevice: Send + Sync {
    fn allocate_buffer(&self, size: usize, alignment: usize) -> Result<BufferHandle, DeviceError>;
    fn bind_sparse_pages(&self, page_table: &PageTableDescriptor) -> Result<(), DeviceError>;
    fn compile_pipeline(&self, ir: &CommandBuffer, plan: &MemoryPlan) -> Result<PipelineHandle, DeviceError>;
    fn submit_step(&self, queue: QueueHandle, pipeline: PipelineHandle, io_binding: &StepBinding) -> Result<(), DeviceError>;
}

```

### 2.4 `sl-core`（模型装配与单步驱动微内核）

-   **职责：** 连接图规划、模型权重与硬件接口，提供确定性的单步推进能力。
    
      
    
-   **边界约束：** 严禁包含网络协议、多线程池管理、多请求优先级排序或动态 `malloc`。
    
      
    
-   **核心契约：**
    
      
    

Rust

```
pub struct StepContext<'a> {
    pub batch_size: usize,
    pub token_ids: &'a [u32],
    pub seq_positions: &'a [u32],
    pub page_table_bindings: &'a [PhysicalPageId],
}

impl CoreEngine {
    /// 初始化阶段：完成权重绑定、图编译与静态内存校验（仅调用一次）
    pub fn build(config: ModelConfig, weights: MappedWeights, device: Arc<dyn BackendDevice>) -> Result<Self, CoreError>;

    /// 运行阶段：执行单步前向传播，结果直接写入预分配的 output_logits 缓冲区
    pub fn step(&self, ctx: &StepContext, scratchpad: &mut [u8], output_logits: &mut [f32]) -> Result<(), CoreError>;
}

```

### 2.5 `sl-daemon`（进程树管理与会话编排器）

-   **职责：** 采用 Master-Worker 进程模型。Master 负责监听外部 IPC（Unix Domain Socket / Named Pipe）、管理并发会话状态、执行 Continuous Batching 组批策略以及全局空闲 Page 分配；Worker 进程驻留 `CoreEngine` 实例，通过共享内存（Shared Memory）接收 `StepContext` 并执行计算。
    
      
    

## 3. 发行版架构设计（Distribution Architecture）

StarLight 不发布单一的臃肿运行时，而是通过组合上述基础模块，构建面向特定场景的**发行版（Distro）**。发行版仓库不包含算法实现，仅包含依赖声明（`Cargo.toml`）与不足百行的初始化装配代码。

  

### 3.1 官方标准发行版矩阵

**发行版名称**

**目标运行环境**

**装配模块清单**

**调度与内存特征**

**StarLight-Nano**

端侧设备、AIPC、嵌入式环境

`sl-core` + `sl-graph` + `backend-cpu` / `backend-vulkan` + `ve-python`

**无 `sl-daemon` 守护进程**；进程内直通调用；线性指令重放；利用 `mmap` 与统一内存实现零拷贝加载；支持空闲资源挂起。

**StarLight-Cluster**

裸金属服务器、多卡推理集群

`sl-core` + `sl-graph` + `backend-cuda` + `sl-daemon` + `ve-comm` (通信插件)

Master-Worker 进程隔离；启用 Continuous Batching 动态组批；预分配大页显存池；集成跨卡集合通信算子节点。

### 3.2 模块重写与第三方组件拼接指南

系统架构天然支持开发者或第三方合作方针对特定需求，替换任意层级的组件或拼接外部库：

  

#### 场景 A：接入新型硬件或专用加速卡（新增或替换 `backend-*`）

1.  创建独立 Crate（如 `backend-npu`），仅依赖 `sl-device` 与 `sl-precision`。
    
      
    
2.  实现 `BackendDevice` Trait，将 `CommandBuffer` 中的标准算子枚举映射至硬件厂商的底层 C-API 或专有指令集。
    
      
    
3.  在发行版入口处将设备实例化对象替换为 `NpuDevice::new()`，`sl-core` 与上层业务代码无需任何改动。
    
      
    

#### 场景 B：拼接第三方高性能算子库（混合后端重写）

若需在特定平台上直接复用成熟第三方库（如在 CPU 上局部调用 `oneDNN`，或在特定 GPU 上调用定制 `CUTLASS` 内核）：

  

1.  在对应 `backend-*` 内部通过 FFI 封装第三方函数。
    
      
    
2.  遵循零分配原则：将 `sl-graph` 规划好的 `scratchpad` 偏移指针直接作为第三方算子的 Workspace 内存传入，接管其内部内存分配器。
    
      
    

#### 场景 C：定制私有业务调度器（替换 `sl-daemon`）

若外部系统已有成熟的微服务网关或 C++/Go 编写的调度框架：

  

1.  直接丢弃 `sl-daemon` 模块。
    
      
    
2.  通过 C-ABI 导出 `sl-core` 的 `build` 与 `step` 接口。
    
      
    
3.  外部框架自行管理请求队列与页表整数数组，按节拍调用 C 接口驱动底层计算。
    
      
    

## 4. 代码仓库拓扑与多团队协同规范

### 4.1 仓库物理结构（Git Submodule 隔离）

主仓库仅维护版本指针与发行版装配代码，各核心模块作为独立 Git 仓库存在，确保权限隔离与独立演进：

  

Plaintext

```
starlight-workspace/              # [主控与发行版仓库]
├── .gitmodules                   # 记录各独立模块仓库 URL 与 Commit Hash
├── Cargo.toml                    # Workspace 全局编译配置
├── crates/
│   ├── sl-precision/             # [Submodule] 独立仓库: SeekStarAI/sl-precision
│   ├── sl-graph/                 # [Submodule] 独立仓库: SeekStarAI/sl-graph
│   ├── sl-device/                # [Submodule] 独立仓库: SeekStarAI/sl-device
│   ├── sl-core/                  # [Submodule] 独立仓库: SeekStarAI/sl-core
│   └── backends/
│       ├── backend-cpu/          # [Workspace crate] CPU SIMD 算子后端
│       └── backend-vulkan/       # [Workspace crate] Vulkan/SPIR-V 计算后端
├── services/
│   └── sl-daemon/                # 本地 workspace crate：进程监管与会话编排
├── distros/                      # 发行版装配目录
│   ├── starlight-nano/           # 端侧发行版入口与 PyO3 绑定
│   └── starlight-cluster/        # 集群服务发行版与 Daemon 集成
└── tests/
    └── golden-baselines/         # 跨模块联合检验的标准输入输出二进制基准

```

### 4.2 开发者协同与提交流程

1.  **拉取工作区：** `git clone --recurse-submodules <workspace-url>`。
    
      
    
2.  **模块独立开发：** 开发者进入认领的模块子目录（如 `cd crates/sl-graph`），创建特性分支开发。所有代码提交与 PR 直接推送至该模块的独立仓库，严禁污染主控仓库历史。
    
      
    
3.  **契约变更管控：** 任何涉及 `sl-device` 或 `sl-core` 公共签名（Trait/Struct）的修改，必须先提交架构变更提案（RFC），经核心组评审合并后，其余模块方可同步更新 Submodule 指针。

## 6. 联合调试与持续集成规范（CI & Integration Rules）

1.  **目录级开发文档：** 每个子模块根目录下必须维护 `DEVELOPMENT.md`，明确记录该模块的输入输出字节序要求、对齐假设以及本地单测运行指令。
    
      
    
2.  **黄金基准测试（Golden Reference Check）：** `tests/golden-baselines/` 存放标准模型单层与整网的固定输入 Token、预期输出 Logits 及各层中间激活值快照。任何算子优化或图融合 Pass 合并前，必须通过 CI 的基准比对测试。
    
      
    
3.  **零分配门禁（Zero-Alloc Gate）：** CI 流水线在运行 `sl-core` 与 `backend-*` 的基准测试时，全局替换 Rust 的 `#[global_allocator]` 为监控分配器。一旦在 `step()` 执行期间捕获到任何堆内存申请调用，CI 直接判定构建失败。
